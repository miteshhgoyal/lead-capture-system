## 4. Phone Normalization Rules with Worked Examples

### Normalization Implementation
The normalization function `normalizePhone` is located in `lib/validation/lead.ts`, lines 31–54:

```typescript
export function normalizePhone(rawPhone: string, defaultCountryCode: string = "+91"): string {
  if (!rawPhone) return "";
  let cleaned = rawPhone.replace(/[^\d+]/g, "").trim();

  // Step 1: If already starts with '+', ensure digits follow
  if (cleaned.startsWith("+")) {
    const digits = cleaned.slice(1).replace(/\D/g, "");
    return `+${digits}`;
  }

  // Step 2: Remove leading 0s often entered in India/UK/etc.
  cleaned = cleaned.replace(/^0+/, "");

  // Step 3: Format country code
  const cCode = defaultCountryCode.startsWith("+") ? defaultCountryCode : `+${defaultCountryCode}`;
  const cCodeDigits = cCode.replace(/\D/g, "");

  // Step 4: Check if cleaned already starts with country code digits
  if (cleaned.startsWith(cCodeDigits) && cleaned.length > cCodeDigits.length + 6) {
    return `+${cleaned}`;
  }

  // Step 5: Prepend country code
  return `${cCode}${cleaned}`;
}
```

### Normalization Flow & Step-by-Step Rules
1. **Sanitize:** Strip all non-digit and non-`+` characters (`[^\d+]`).
2. **Explicit Plus Override (Step 1):** If the input starts with `+`, strip all subsequent non-digits and immediately return `+<digits>`. **`defaultCountryCode` is completely ignored.**
3. **Leading Zero Removal (Step 2):** Strip leading zeroes (`^0+`).
4. **Country Code Digits Check (Step 4):** If the cleaned string starts with `cCodeDigits` AND has more than 6 digits after the prefix (`cleaned.length > cCodeDigits.length + 6`), prepend a `+` and return.
5. **Fallback Prepend (Step 5):** Prepend `cCode` directly to `cleaned`.

### Why Phone and CountryCode Can Disagree in Stored Leads
There are three distinct code mechanisms that cause stored `phone` and `countryCode` to disagree:

1. **User Types International Prefix with Disagreeing Dropdown:**
   If a user has `countryCode` dropdown set to `+91` (the default) but types `+1 415 555 2671` in the phone field, Step 1 triggers.
   - Output `phone`: `"+14155552671"`
   - Stored `countryCode`: `"+91"` (from dropdown payload)
   - Disagreement: `phone` has country code `+1`, while `countryCode` has `+91`.
2. **User Enters Disagreeing Digits Without Plus:**
   If a user selects `+44` (UK) in the dropdown, but enters an Indian 10-digit number `9876543210`:
   - `cCodeDigits` is `44`.
   - `cleaned` does not start with `44`.
   - Step 5 executes: prepends `+44`.
   - Stored `phone`: `"+449876543210"`.
   - Stored `country`: `"United Kingdom"`.
   - The number is actually an Indian subscriber number prefixed with the UK code.
3. **Duplicate Submission Field Preservation:**
   When a duplicate lead is submitted matching on email (`app/api/leads/route.ts:95–110`):
   - `existing.country` is updated: `existing.country = data.country;`
   - **`existing.phone` is NOT updated.**
   - **`existing.countryCode` is NOT updated.**
   - If a lead originally registered with `+919876543210` (`countryCode: "+91"`, `country: "India"`), and later re-registers with the same email from the US (`country: "United States"`, `countryCode: "+1"`), the database doc becomes:
     - `country`: `"United States"`
     - `countryCode`: `"+91"`
     - `phone`: `"+919876543210"`
   - `country` and `countryCode` now disagree.

## 5. Partner Resolution and the Slug vs PartnerId Explanation

### Resolution Logic on Lead Submission
Located in `app/api/leads/route.ts`, lines 45–65:
1. **Client Submission:** The frontend sends `partnerSlug` in the JSON request body (e.g. `{ "partnerSlug": "aman-singh", ... }`).
2. **Server-Side Defaults:**
   ```typescript
   let partnerId = null;
   let partnerSlug = "direct";
   let partnerName = "Direct";
   let source: "partner-page" | "direct" = "direct";
   ```
3. **Database Lookup:**
   ```typescript
   const requestedSlug = (json.partnerSlug || "").trim().toLowerCase();
   if (requestedSlug && requestedSlug !== "direct") {
     const partner = await Partner.findOne({ slug: requestedSlug, isActive: true }).lean();
     if (partner) {
       partnerId = partner._id;
       partnerSlug = partner.slug;
       partnerName = partner.name;
       source = "partner-page";
     }
   }
   ```
4. **Fallback:** If `requestedSlug` is missing, empty, `"direct"`, non-existent in the database, or has `isActive: false`, the lead is silently assigned to `partnerSlug = "direct"`, `partnerName = "Direct"`, `partnerId = null`, and `source = "direct"`.

### Can Partner Fields Be Missing or Empty?
- `partnerSlug`: **Never empty or missing** on a valid lead document. The Mongoose model defines `required: true`. If unresolved, it defaults to `"direct"`.
- `partnerName`: **Never empty or missing**. The Mongoose model defines `required: true`. Defaults to `"Direct"`.
- `partnerId`: **Can be null / missing.** For all `"direct"` leads (and leads submitted for inactive/unknown slugs), `partnerId` is stored as `null`.

### The Partner Model and Slug Uniqueness
In `lib/models/Partner.ts`:
- Field: `slug: { type: String, required: true, lowercase: true, trim: true }` (lines 59–64).
- Unique Index: `partnerSchema.index({ slug: 1 }, { unique: true })` (line 87).
At any given moment, each active partner document in the `partners` collection has a unique `slug`.

### Why the Same `partnerSlug` Appears Under Different `partnerId` Values
This occurs for three code-driven reasons:

1. **Partner Deletion and Re-creation:**
   In `app/api/admin/partners/[id]/route.ts:138`, partners can be hard-deleted via `Partner.findByIdAndDelete(id)`.
   When partner "aman-singh" (`_id: ObjectId("673700000000000000000001")`) is deleted, all existing leads in the `leads` collection retain `partnerSlug: "aman-singh"` and that original `partnerId`.
   If an administrator later creates a new partner with the slug `"aman-singh"`, MongoDB generates a new `_id` (`ObjectId("673799999999999999999999")`). New leads will receive the new `partnerId`, while old leads retain the old `partnerId`.
2. **Database Seeding and Environment Drops:**

## 6. Duplicate Logic

### Duplicate Lookup Key
In `app/api/leads/route.ts`, lines 86–89:
```typescript
const existing = await Lead.findOne({
  partnerSlug,
  $or: [{ phone: normalizedPhone }, { email: normalizedEmail }],
});
```
The exact lookup condition is:
**`partnerSlug` MATCHES AND (`phone` MATCHES OR `email` MATCHES).**

### Key Characteristics:
1. **Partner Isolation:** Duplicate detection is partitioned by `partnerSlug`. If a user with phone `+919876543210` registers for partner `"aman-singh"` and also registers for partner `"direct"`, they are stored as **two separate, original documents**. Neither is marked as duplicate.
2. **Time Window:** **There is NO time window.** Duplicate detection queries the entire collection across all time.
3. **Compound Key:** A match on **either** normalized phone **or** normalized email under that partner qualifies as a duplicate.

### Document Creation vs In-Place Update
A duplicate submission is **NOT a new document**. It performs an **in-place update** on the existing document (`existing.save()`, `app/api/leads/route.ts:111`). No secondary lead document is inserted.

### Field Overwrite Behavior (app/api/leads/route.ts:94–110)

| Field | Behavior on Duplicate Submission | Reason / Implementation |
| :--- | :--- | :--- |
| `_id` | **Preserved** | Existing document is updated in place. |
| `createdAt` | **Preserved** | Mongoose preserves original creation timestamp. |
| `name` | **Overwritten** | Updated to latest submitted name (`existing.name = data.name`). |
| `age` | **Overwritten** | Updated to latest submitted age (`existing.age = data.age`). |
| `profession` | **Overwritten** | Updated to latest submitted profession (`existing.profession = data.profession`). |
| `capital` | **Overwritten** | Updated to latest submitted capital (`existing.capital = data.capital`). |
| `country` | **Overwritten** | Updated to latest submitted country (`existing.country = data.country`). |
| `isDuplicate` | **Set to `true`** | Flagged as duplicate (`existing.isDuplicate = true`). |
| `duplicateCount`| **Incremented** | `existing.duplicateCount = (existing.duplicateCount \|\| 0) + 1`. |
| `phone` | **PRESERVED** | **Never overwritten.** Retains the phone number from the original submission. |
| `countryCode` | **PRESERVED** | **Never overwritten.** Retains the dial code from the original submission. |
| `email` | **PRESERVED** | **Never overwritten.** Retains the email from the original submission. |
| `status` | **PRESERVED** | Does not reset to `"new"`. Preserves counselor status (`"contacted"`, `"joined"`). |
| `notes` | **PRESERVED** | Existing counselor notes are retained untouched. |
| `partnerId` | **PRESERVED** | Retains original partner association. |
| `partnerSlug` | **PRESERVED** | Retains original partner slug. |
| `partnerName` | **PRESERVED** | Retains original partner name. |
| `source` | **PRESERVED** | Retains original source (`"partner-page"` or `"direct"`). |
| `utm_source` | **Conditionally Overwritten** | Updated if `data.utm_source` is present in second submission. |
| `utm_medium` | **Conditionally Overwritten** | Updated if `data.utm_medium` is present in second submission. |
| `utm_campaign` | **Conditionally Overwritten** | Updated if `data.utm_campaign` is present in second submission. |
| `utm_term` | **PRESERVED** | Not updated on duplicates (omitted from lines 102–106). |
| `utm_content` | **PRESERVED** | Not updated on duplicates (omitted from lines 102–106). |
| `referrer` | **Conditionally Overwritten** | Updated if `data.referrer` is present. |
| `landingUrl` | **Conditionally Overwritten** | Updated if `data.landingUrl` is present. |
| `ip` | **Overwritten** | Updated to latest submission IP. |
| `userAgent` | **Overwritten** | Updated to latest User-Agent. |
| `device` | **Overwritten** | Updated to latest detected device. |
| `updatedAt` | **Updated** | Mongoose automatically sets current timestamp. |

### Which Document is "The Original"?
The single document in MongoDB **is the original record** (`_id` and `createdAt` represent the initial submission). However, its profile attributes (`name`, `age`, `profession`, `capital`, `country`, `ip`, `device`) represent the **latest** submission values.

### Common Read Pattern Support Analysis

| Read Pattern | Supported by Declared Indexes? | Supporting Index |
| :--- | :--- | :--- |
| Duplicate lookup (`partnerSlug` + `phone`) | **Yes (Exact match)** | `{ partnerSlug: 1, phone: 1 }` |
| Duplicate lookup (`partnerSlug` + `email`) | **Yes (Exact match)** | `{ partnerSlug: 1, email: 1 }` |
| Filter by `partnerSlug`, sort `createdAt DESC` | **Yes (Index scan)** | `{ partnerSlug: 1, createdAt: -1 }` |
| Filter by `createdAt` range | **Yes (Range scan)** | `{ createdAt: -1 }` |
| Sort by `createdAt ASC` | **Yes (Reverse scan)** | B-tree index on `{ createdAt: -1 }` traversed backwards |
| Filter by `isDuplicate` | **Yes (Single key)** | `{ isDuplicate: 1 }` |
| Filter by `phone` | **Yes (Single key)** | `{ phone: 1 }` |
| Filter by `status`, sort `createdAt DESC` | **Yes (Index scan)** | `{ status: 1, createdAt: -1 }` |
| Filter by `capital` or `country` | **NO INDEX** | Requires full collection scan |
| Text search on `name`, `phone`, `email` (`q`) | **NO (Partial)** | Uses case-insensitive regex (`$options: "i"`), causing full table scans |

## 9. Data-Quality Risks and How to Detect Them

| Risk Factor | Root Cause in Code | Impact on Data | Detection / Query Method |
| :--- | :--- | :--- | :--- |
| **Honeypot Bot Submissions** | Hidden field `hp_company` in `LeadFormSchema` (`lib/validation/lead.ts:81-82`). | Automated bots that fill hidden fields receive a fake HTTP 200 and are **discarded before writing to DB** (`app/api/leads/route.ts:26-29`). Zero bot leads with `hp_company` reach DB. | Verified clean at API layer. |
| **IP-Level Spam / Floods** | Rate limit is 10 requests per 60 seconds per IP (`app/api/leads/route.ts:15`). | Distributed botnets or rotating proxies can submit up to 10 leads/min per IP. | Group by IP: `db.leads.aggregate([{ $group: { _id: "$ip", count: { $sum: 1 } } }, { $match: { count: { $gt: 10 } } }])`. |
| **No CAPTCHA / Proof of Work** | There is no Turnstile, reCAPTCHA, or puzzle challenge. | Automated scripts ignoring `hp_company` can submit validly formatted fake leads. | Check submission intervals and repetitive email domains (`@gmail.com` with random character strings). |
| **No OTP / Verification** | Email and phone are not verified with OTP. | Users can submit junk or mistyped phone numbers (`9876543210`, `9999999999`) or dummy emails. | Filter for known dummy patterns: `phone: /^\+91(9876543210\|9999999999\|1234567890)$/`. |
| **Phone / CountryCode Desync** | `normalizePhone` overrides dial code if user types `+` (`lib/validation/lead.ts:36`). | Lead document has mismatched `phone` and `countryCode` (e.g. `phone: "+15551234567"`, `countryCode: "+91"`). | Find where `phone` does not start with `countryCode`: see section 10 query. |
| **Country Overwrite on Duplicate** | Duplicate submissions overwrite `country`, but **leave `phone` and `countryCode` unchanged** (`app/api/leads/route.ts:98`). | Lead doc shows country as `"United States"`, but phone as `"+919876543210"` with `countryCode: "+91"`. | Query: `db.leads.find({ isDuplicate: true, country: "United States", countryCode: "+91" })`. |
| **Missing Mongoose Enum on Capital & Profession** | `lib/models/Lead.ts:51-52` lacks `enum` definitions. | Any direct MongoDB insert or legacy import may have created capital or profession values that do not match `CAPITAL_OPTIONS` or `PROFESSION_OPTIONS`. | Distinct query: `db.leads.distinct("capital")` and `db.leads.distinct("profession")`. |
| **Internal Staff / Test Leads** | Developers and staff submit forms during testing. No `isTest` flag exists. | Live leads collection polluted with test records. | Filter by name, email, or test notes: `db.leads.find({ $or: [{ name: /test/i }, { email: /test\|admin\|demo/i }] })`. |
| **Unlinked Partners** | Lead submitted with invalid/inactive partner slug defaults to `partnerSlug = "direct"` and `partnerId = null`. | Marketing attribution lost if partner link had a typo. | Review leads with `landingUrl` containing a slug but stored as `partnerSlug: "direct"`. |
